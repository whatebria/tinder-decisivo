Findings P0 · bugs latentes

Estos cuatro rompen tsc en HEAD (verificado) o generan comportamiento incorrecto silencioso. Bloquean cualquier refactor grande hasta resolverlos.

▶ P0.1 Invalidate a queryKey inexistente
hooks.ts:346

useActualizarComuna invalida ["match"] (singular), pero los keys reales son ["matches", ...] y ["match-detalle", ...]. Cambiar de comuna no invalida los matches aunque el backend sí los recalcula. 

// hooks.ts:346
qc.invalidateQueries({ queryKey: ["match"] });   // ← singular, no matchea nada

Fix: cambiar a ["matches"] o usar helper de queryKeys.

▶ P0.2 NewsCard sin prop mentionedCandidates
NoticiasScreen.tsx:302

tsc falla en HEAD. La screen pasa un prop que la interface del componente no declara.

error TS2322: Property 'mentionedCandidates' does not exist
  on type 'IntrinsicAttributes & NewsCardProps'.

Fix: agregar el prop a NewsCardProps (parte del workstream nuevo).

▶ P0.3 ResultadoHero rompió contrato con consumers
catalog/organisms · ResultadosScreen

ResultadoHero ya no declara isDecision en su interface, pero catalog/organisms/candidate.tsx:196 y ResultadosScreen.tsx:379 siguen pasándolo. En strict mode, props extra rompen.

Fix: sacar isDecision de ambos consumers (parte del workstream «delete decision»).

▶ P0.4 Import huérfano a MiDecisionScreen
AppNavigator.tsx:20

Se borró el archivo MiDecisionScreen.tsx pero el import quedó en AppNavigator.tsx. tsc rompe.

Fix: borrar el import + la ruta del stack.

Findings P1 · mantenibilidad & escalabilidad

▶ P1.1 queryKeys centralizados abandonados
DRY

queryClient.ts define un helper queryKeys, pero hooks.ts lo ignora en 8 lugares.

queryKey hardcoded Debería usar
["matches", tipoEleccionId]queryKeys.matches(...)
["misRespuestas", ...] (x2)queryKeys.misRespuestas(...)
["match-detalle", candidatoId]queryKeys.matchDetalle(...)
["posturas", ...]queryKeys.posturas(...)
["perfil"]queryKeys.perfil
["regiones"]queryKeys.regiones
["comunas", ...]queryKeys.comunas(...)
["noticias", ...] (feed) colisiona por prefix con queryKeys.noticiasCandidato

Recomendación: promover todo a helpers y separar namespaces (["noticias", "feed", ...] vs ["noticias", "porCandidato", id]).

▶ P1.2 nombreCompleto/iniciales duplicados en 3 screens
DRY + idioma

utils/candidato.ts exporta ambas funciones. Sin embargo:

Screen Duplica como Idioma
CompararScreen.tsx:61,66nombreCompleto, inicialeses
DetalleCandidatoScreen.tsx:76,80fullName, initialsen
MisGuardadosScreen.tsx:64,155fullName, initials (signature distinta)en

Impacto: mezcla de idiomas (regla del proyecto: español neutro), 3 implementaciones divergentes, cambios locales que no propagan.

Fix: borrar las locales e importar de utils/candidato. Refactor mecánico.

▶ P1.4 Modal molecule sub-adoptada
5 modales legacy

ConfirmModal ya está migrado en el stash. Faltan 5 modales que siguen implementando backdrop/card/shadows a mano en vez de consumir <Modal>:

  • PreguntaInfoModal
  • ShareModal
  • CambiarPasswordModal

▶ P1.5 Types duplicados entre endpoints.ts y types/api.ts
contrato

Pattern inconsistente. Para Candidato, Pregunta, Noticia usás alias del schema OpenAPI. Para Perfil, Region, ComunaInline, NoticiaBookmark, MatchDetalle, MiRespuesta… declarás la interface a mano.

Riesgo: si el backend cambia el shape, los alias se actualizan con types:gen, las interfaces manuales no. Bug latente esperando.

Fix: migrar todas a Schemas["X"] cuando existan en el schema.

▶ P1.6 useCandidato(id) refetchea la lista completa
performance

Ya está el comentario «si crece a >100 candidatos, agregar endpoint dedicado», pero el queryKey es queryKeys.candidato(id) — cada useCandidato(id) hace un fetch completo. Falta reusar el cache. 

// Fix: leer del cache antes de fetchear
const cached = queryClient.getQueryData<Candidato[]>(queryKeys.candidatos);
if (cached) return cached.find(c => c.id === id) ?? null;
// ...else fetch
▶ P1.7 apiClient sin retry ni cancel token
resiliencia

Requests fuera de React Query (login, submit, mutations) van sin retry. Aceptable, pero conviene documentar la decisión o aplicar retry a nivel axios interceptor para operaciones idempotentes.

Cierre ejecutivo

El código está en una excelente posición para escalar: atomic design, tokens, dark mode, WCAG y typing end-to-end ya están resueltos. Los findings son deuda técnica localizada, no problemas estructurales. Prioridad 1: terminar el workstream de «delete decision» para desbloquear tsc. Prioridad 2: fixes mecánicos de DRY (P0.1, P1.1, P1.2) — probablemente 1-2 horas. Prioridad 3: refactor de las 2 screens gigantes con un patrón reutilizable (custom hook de filtros + sub-componentes por tab) que después se replica en Candidatos. Los tests son la deuda más grande pero también la que menos bloquea shippear.
