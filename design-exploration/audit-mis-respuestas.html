Fase 2 · Auditoria UX / UI Profunda
UX
Boton "Reiniciar" neutro para accion destructiva: el boton de ghost (sin color) inicia el flujo de borrar todas las respuestas. El usuario que lo toca sin leer el texto del introRow podria no anticipar el impacto. El ConfirmModal es excelente, pero la señal de peligro deberia empezar antes -- en el boton mismo, con texto danger o borde danger.
RespuestaCard: affordance solo textual: la unica senal de que la card es interactiva es el hint "Toca para editar" (typography.overline, c.textTertiary). No hay chevron ni icono de edicion. Para usuarios que no leen hints, la card parece contenido de solo lectura.
Orden de grupos por eje no garantizado: el orden de los ejes tematicos en la pantalla depende del orden en que las respuestas llegan del backend. Si el backend cambia el orden, la pantalla cambia visualmente sin que el usuario lo controle.
UI / Design System
opActual en c.primary (azul): la opcion de respuesta elegida se muestra en c.primary. DS-11 especifica primary para CTAs de accion, no para contenido seleccionado. Para un estado "elegido" podria ser mas apropiado c.secondary (verde) o c.text con fontWeight distinguible.
hint "Toca para editar" siempre visible: a diferencia del caso de BUG-017 (hint visible sin contenido disponible), en este caso el hint si es relevante siempre. Pero visualmente la card podria comunicar interactividad con un icono en lugar de texto, liberando espacio.
introRow mezcla texto instructivo con accion destructiva: el texto "Toca cualquier pregunta para modificar tu respuesta" y el boton "Reiniciar cuestionario" estan en la misma fila horizontal. Son dos tipos de contenido muy distintos (instruccion vs accion peligrosa) en el mismo contenedor visual.
Fase 3 · Benchmarking
Duolingo
Boton de reset con color danger desde el principio
El boton de "Reiniciar progreso" en Duolingo siempre es rojo desde que aparece en la UI, antes del dialogo de confirmacion. El usuario recibe la señal de riesgo desde el primer punto de contacto.
Adaptacion: cambiar Button variant="ghost" a variant="danger" (o un estilo de texto danger sin relleno) en el boton de Reiniciar.
iOS Ajustes
Chevron como indicador universal de interactividad
Cada fila interactiva de iOS Settings tiene un chevron (›) a la derecha. El usuario aprende rapidamente que chevron = hay mas, tap abre algo. Sin chevron = solo lectura.
Adaptacion: agregar un icono de lapiz o chevron a la RespuestaCard para que sea visualmente obvio que es editable.
Google Forms (respuestas)
Respuesta seleccionada con color semantico
La opcion seleccionada se muestra con el color de marca del formulario, claramente diferenciada de las no seleccionadas. El color no es el de los CTAs de accion -- es un color de estado.
Adaptacion: usar c.secondary (verde) para opActual en lugar de c.primary (azul). Verde = seleccionado/confirmado, azul = accion.
Linear
Acciones destructivas separadas del contenido
En Linear, las acciones de borrado o reset estan en una seccion propia al fondo de la pantalla, separadas visualmente del contenido de trabajo con un separador.
Adaptacion: mover el boton Reiniciar de la fila de intro a una seccion propia al final de la pantalla, con fondo danger-bg.
Notion
Orden explicito de secciones
Las propiedades de una pagina en Notion se muestran siempre en el mismo orden, independientemente del orden en que se crearon o de la API. El usuario desarrolla un modelo mental del orden.
Adaptacion: ordenar los grupos de eje tematico con un orden fijo (por nombre alfabetico o por el orden del DS-11) en lugar de depender del orden de la API.
Fase 4 · Problemas Detectados
Alto
P-A01 · Boton "Reiniciar cuestionario" usa variant="ghost" para accion destructiva
El boton que inicia el flujo de reinicio usa variant="ghost" (texto sin relleno, color neutral). La accion borra todas las respuestas del usuario para ese tipo de eleccion -- irreversible. El ConfirmModal es correcto, pero la señal de peligro deberia comenzar en el boton, no en el modal. Un usuario que toca el boton sin leer el contexto no anticipa el riesgo.
MisRespuestasScreen.tsx L260: <Button variant="ghost" size="sm">Reiniciar cuestionario</Button>
Medio
P-M01 · RespuestaCard sin affordance visual de interactividad
La unica senal visual de que la card es editable es el texto "Toca para editar" en typography.overline con c.textTertiary (muy tenue). No hay chevron ni icono de edicion. Usuarios que no leen hints pueden asumir que el contenido es solo lectura.
P-M02 · opActual en c.primary -- token de CTA para estado seleccionado
La opcion de respuesta elegida se muestra en c.primary (azul). DS-04 asigna primary a CTAs de accion. Para un estado "seleccionado/elegido", el token mas correcto es c.secondary (verde = confirmado) o typography sin color especial pero con fontWeight diferencial.
MisRespuestasScreen.tsx L357: <Text style={[styles.opActual, { color: c.primary }]}>
P-M03 · handleSave y handleConfirmReiniciar sin useCallback
Ambos handlers async se recrean en cada render y se pasan como props a EditarRespuestaModal y ConfirmModal. El impacto es limitado porque los modales solo se montan cuando estan visibles, pero el patron es inconsistente con las buenas practicas del proyecto.
P-M04 · Orden de grupos por eje dependiente del orden de la API
El orden en que aparecen los grupos de eje tematico (Economia, Sociedad, etc.) depende del orden de insertion en el Map, que a su vez depende del orden de las respuestas en la API. Si el backend cambia el orden, la pantalla cambia visualmente sin una razon aparente para el usuario.
Bajo
P-L01 · PESO_LABELS sin test -- fallback expone datos crudos
Si el backend envia un peso fuera del rango 0-3, el fallback muestra "peso N" al usuario (dato crudo). Deberia ser un string mas amigable. Ademas, sin test, si el rango cambia, la UI falla silenciosamente.
MisRespuestasScreen.tsx L367: PESO_LABELS[respuesta.peso] ?? `peso ${respuesta.peso}`
P-L02 · Fallback "(opcion desconocida)" hardcodeado
El string de fallback cuando no se encuentra la opcion elegida deberia ser una constante de modulo, no un string literal inline.
MisRespuestasScreen.tsx L354: opActual?.texto ?? "(opcion desconocida)"
Fase 5 · Propuesta de Rediseno
Bloque 1 — Boton Reiniciar con señal danger
Problema: variant="ghost" para accion destructiva
Cambio: Cambiar a un estilo de texto danger. Como Button no tiene variant="danger-ghost", se puede usar variant="ghost" con una prop textStyle={{color:c.danger}}, o agregar variant="danger-ghost" al componente Button.
Alternativa: Mover el boton Reiniciar a una seccion de DangerZone al final de la pantalla (mas limpio arquitecturalmente).
Beneficio: El primer contacto con la accion destructiva ya comunica peligro.
Bloque 2 — RespuestaCard con chevron
Problema: affordance solo textual
Cambio: Agregar un icono chevron (›) o de edicion (lapiz) alineado a la derecha de la card. Esto convierte el hint textual en un indicador visual universal.
Beneficio: El usuario sabe que puede editar sin leer el hint.
Patron: iOS Settings, NavRow de la misma app
Bloque 3 — opActual con c.secondary
Problema: c.primary (CTA) para estado seleccionado
Cambio: Reemplazar c.primary por c.secondary para la opcion elegida.
Beneficio: Verde = seleccionado/confirmado, semantica correcta.
Patron UX: DS-04 semantica de colores
Bloque 4 — Orden explicito de grupos
Problema: orden dependiente del orden de la API
Cambio: Ordenar grupos.sort() por nombre de eje (alfabetico) o por un orden fijo definido en domain/dimensiones.ts.
Beneficio: El usuario desarrolla un modelo mental estable de la pantalla.
