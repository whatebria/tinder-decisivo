Flujo del usuario
4 origenes distintos:
1. Resultados → DetalleCandidato (con matchPct + breakdown)
2. Candidatos → DetalleCandidato (con o sin matchPct)
3. Guardados → DetalleCandidato
4. Comparar → DetalleCandidato

Variantes de estado:
- Usuario autenticado con match calculado (estado completo)
- Usuario autenticado sin cuestionario (emptyMatchBlock)
- Usuario invitado (sin ActionRow, sin MatchExplanation)

Puntos de abandono:
- Sin "Ver todas las posturas" en ResumenTab
- Sin count badge en la tab Posturas para motivar el cambio
Objetivo funcional
Que resuelve: contexto completo del candidato para tomar la decision de voto
Tarea principal: evaluar la compatibilidad y las posturas del candidato
KPI impactado: confianza en la decision de voto, tiempo de evaluacion
Conversion: usuario sin match → iniciar cuestionario

Tension actual: las posturas destacadas (3) en el ResumenTab no tienen CTA para ver todas, forzando al usuario a descubrir la tab "Posturas" por si mismo. Sin hint de discoverability.

Fase 2 · Auditoria UX / UI Profunda
UX
Discoverability zero de la tab Posturas: el usuario ve "Posturas destacadas" con 3 items en el ResumenTab. No hay indicacion de que hay mas, no hay CTA "Ver todas", no hay count visible. El usuario tiene que descubrir solo que existe la tab "Posturas" con el numero completo.
Semantica visual del descartar activo: cuando el candidato esta descartado, el boton X tiene fondo azul (primary solid). El azul en la app comunica afinidad y acciones positivas. Un candidato descartado deberia tener el boton con fondo danger, no primary.
Confianza estadistica vs afinidad en el mismo chip: el MatchTier fue disenado para afinidad entre usuario y candidato (alta/media/baja coincidencia). En este screen se reutiliza para expresar la confianza estadistica del calculo (ALTA/BAJA del backend). Son dos conceptos distintos que el usuario podria confundir.
ActionRow sin labels visuales: 3 IconButtons sin texto visible. En mobile los iconos de corazon, X y link son reconocibles — pero el link (compartir) podria confundirse con "abrir en navegador" o "copiar URL del perfil".
UI / Design System
ProfileHero usa c.accent2 como fondo: DS-11 P6: "Header background → --color-brand-hero o foto". c.accent2 es el token definido en DS-04 para el estado hover de botones e interacciones secundarias. Usarlo como fondo de un hero institutcional es una violacion semantica del sistema de tokens.
Badge variant="info" para el partido: DS-04 dice que "info" es azul para informacion contextual. El partido de un candidato no es informacion contextual — es identidad. Visualmente correcto (badge azul es legible), pero semanticamente incorrecto.
Mobile first — ActionRow: los 3 botones de 40px cumplen el minimo de tap target WCAG 2.5.5 (44px es el ideal, 40px es acceptable). Sin embargo, el gap entre botones es sp3 (~12px), lo que en mobile angosto puede generar taps accidentales.
CandidatoPosturas hint "Toca para ver justificacion": aparece aunque no haya justificacion. El usuario toca y no pasa nada visible (la View condicional esta vacia). Feedback incorrecto — viola el principio de visibilidad del sistema (Nielsen #1).

Fase 4 · Problemas Detectados
Critico
P-C01 · ProfileHero usa c.accent2 como fondo de hero (token de hover, no de hero)
DS-11 P6: "Header background → --color-brand-hero o foto. Jerarquia y seriedad institucional." El componente ProfileHero con tilt="default" (el unico valor usado en DetalleCandidatoScreen) aplica c.accent2 como backgroundColor. DS-04 define accent2 como el token de estado hover para botones e interacciones — no como un fondo de hero. Usar un token de hover en un hero institutcional es una violacion semantica del sistema de design tokens.
ProfileHero.tsx L49-54: TILT_BG = { left:c.accent2, center:c.bg, right:c.card, default:c.accent2 }
P-C02 · CandidatoPosturas: estado loading usa Text en lugar de Spinner
El estado de carga de posturas muestra un Text con "Cargando posturas..." en lugar del componente Spinner que el DS define para estados de carga. Esto viola la consistencia del sistema (CompararScreen, HomeScreen y DetalleCandidatoScreen propio usan Spinner). El usuario ve un texto plano donde el resto de la app muestra feedback visual animado.
CandidatoPosturas.tsx L65: return (<Text style={{ color: c.textSecondary }}>Cargando posturas...</Text>);
Alto
P-A01 · ActionRow: IconButton "descartar activo" usa fondo primary en lugar de danger
Cuando isDescartado=true, el IconButton del boton X usa variant="solid" cuyo fondo es c.primary (azul). El azul en esta app comunica afinidad positiva. Un candidato descartado activamente deberia tener el boton con fondo danger/rojo, no primary/azul. Esta incongruencia semantica confunde al usuario sobre el estado actual.
DetalleCandidatoScreen.tsx L341: variant={isDescartado ? "solid" : "soft"} — solid usa c.primary bg internamente
P-A02 · ResumenTab: posturas.slice(0, 3) sin CTA para ver todas
El ResumenTab muestra maximo 3 posturas como "Posturas destacadas". No hay CTA "Ver todas", no hay count total. El usuario no sabe cuantas hay, ni que existe una tab dedicada con el listado completo. Para un producto cuyo valor central es el matching por posturas, ocultar las posturas sin pista de discoverability es un problema grave de UX.
ResumenTab.tsx L42: const posturasDestacadas = posturas.slice(0, 3);
P-A03 · CandidatoPosturas: hint "Toca para ver justificacion" aparece sin justificacion
El hint aparece para TODAS las posturas, incluso cuando p.justificacion es null. El usuario toca y la View condicional queda vacia — sin feedback. Viola el principio de visibilidad del sistema (Nielsen #1) y genera una experiencia de bug aparente.
CandidatoPosturas.tsx L86-87: {isOpen && p.justificacion ? ... } y L89: el hint aparece sin condicionar a si hay justificacion
Medio
P-M01 · confianzaToTier: funcion sin test, sin export, falla silenciosa para valores desconocidos
La funcion modulo-local mapea "ALTA"→"high", else→"mid", "BAJA"→"low". Si el backend agrega "MEDIA" como valor explicito, cae a "mid" correctamente pero por coincidencia. Si agrega "VERIFICADA_ALTA" u otro valor, silenciosamente muestra "mid" sin warning.
DetalleCandidatoScreen.tsx L75-80: function confianzaToTier(confianza: string | null)
P-M02 · NoticiasTab: 3 casts as-unknown-as para campos de fecha — schema mismatch
formatWhen() hace tres casteos sucesivos `(n as unknown as { campo? })` para encontrar el campo de fecha correcto entre fecha_publicacion, fecha y created_at. Esto indica que el tipo Noticia del frontend no coincide con la respuesta real de la API. El schema deberia alinearse en lugar de parchear en la UI.
NoticiasTab.tsx L26-32: 3x as unknown as {...} para resolver el campo de fecha
P-M03 · ProfileHero Badge variant="info" para el partido — semantica incorrecta
El partido del candidato se muestra con Badge variant="info" (azul informacional). DS-04: "info → informacion contextual, notificaciones". El partido es identidad, no informacion contextual. Deberia usar variant="neutral" (sin color especifico) o una variante "party" con un color neutral.
ProfileHero.tsx L63: <Badge variant="info">{partido}</Badge>
Bajo
P-RC01 · RadarChart: LABEL_MAP hardcodeado viola DS-11 P6
DS-11 P6: "DimensionCards borde y labels -> getDimensionColors() / via dimensiones.ts. Nunca hardcodeado." El LABEL_MAP en RadarChart.tsx replica los nombres de dimensiones que ya existen en domain/dimensiones.ts. Si se agrega un eje nuevo, hay que actualizar ambos archivos. Es una violacion DRY y del contrato del DS.
RadarChart.tsx L39-48: const LABEL_MAP: Record<string, string> = { ECONOMIA: "Economia", SOCIEDAD: "Sociedad", ... }
P-RC02 · RadarChart: sin alternativa textual accesible (WCAG 1.1.1)
El SVG del radar chart no tiene accessibilityLabel, accessibilityHint, ni ningun rol de accesibilidad en el elemento Svg raiz. Un usuario con VoiceOver o TalkBack activo no recibe ningun dato del chart — el elemento es completamente invisible para lectores de pantalla. WCAG 1.1.1 (Nivel A): todo contenido no-texto requiere una alternativa textual.
RadarChart.tsx L140: <Svg width={size} height={size}> — sin accessibilityLabel, sin accessibilityRole, sin aria-label
P-RC03 · RadarChart: magic numbers sin tokens (radius ratio, label offset, fillOpacity)
radius = size*0.35 (con labels) y size*0.45 (sin labels), label offset = radius+18, fillOpacity=0.25. Ninguno esta documentado ni tiene una constante con nombre. Si el diseno del chart cambia, hay que encontrar los numeros dispersos en el codigo.
RadarChart.tsx L75-76: radius = showLabels ? size * 0.35 : size * 0.45 y L121: polarToCartesian(cx, cy, radius + 18, angle)
P-L01 · fontSize:40 para el porcentaje de match — unico hardcode fuera de escala tipografica
Documentado en el codigo como "excepcion unica". El valor 40 no esta en la escala typography del DS. Considerar agregar un token typography.display2 = { fontSize: 40 } para eliminar el hardcode y hacer la excepcion parte del sistema.
DetalleCandidatoScreen.tsx L433-438: fontSize: 40 con comentario "Excepcion documentada"
P-L02 · buildShareText usa Math.round() directamente en lugar de formatMatchPercentage
buildShareText formatea el matchPct como `${Math.round(matchPct)}%` mientras que la UI usa formatMatchPercentage(). Si formatMatchPercentage cambia su formato (decimales, simbolo), el texto compartido quedaria inconsistente con lo que el usuario ve en pantalla.
DetalleCandidatoScreen.tsx L413: `${Math.round(matchPct)}%` vs L64 import formatMatchPercentage
P-L03 · SHOW_NOTICIAS=false permanente — NoticiasTab potencialmente dead code
Si SHOW_NOTICIAS es siempre false en produccion, toda la tab Noticias y el hook useNoticiasCandidato son dead code (YAGNI). Si es un feature flag activo, documentar cuando se va a activar.
constants/features.ts: SHOW_NOTICIAS, usado en DetalleCandidatoScreen.tsx L222-224
Fase 5 · Propuesta de Rediseno
Bloque 1 — Hero institucional con token correcto
Problema: c.accent2 (hover) como fondo de hero
Cambio: Usar c.primary como fondo en ProfileHero tilt="default". El azul institucional da seriedad y consistencia con DS-11 P6. El avatar con borde blanco semi-transparente sobre azul es el patron estandar (LinkedIn, apps civicas).
Beneficio: Cumplimiento DS-11, seriedad institucional, contraste correcto (texto blanco sobre primary).
Patron UX: Institutional hero (LinkedIn, apps civicas)
Bloque 2 — Posturas destacadas con CTA de discoverability
Problema: Sin pista de que hay mas posturas
Cambio: Agregar al pie de "Posturas destacadas" un link "Ver las N posturas →" que cambia programaticamente la tab activa a "posturas" via el onChangeTab prop.
Beneficio: El usuario descubre la tab Posturas sin necesidad de explorar.
Patron UX: Progressive disclosure con CTA explicito (Spotify, Airbnb)
Requiere: pasar onChangeTab como prop adicional a ResumenTab
Bloque 3 — Estado descartado con color correcto
Problema: Boton X activo con fondo azul (primary)
Cambio: Cuando isDescartado=true, usar variant="solid" con override de backgroundColor a c.danger. O agregar variant="danger-solid" al IconButton.
Beneficio: Semantica visual correcta — rojo = candidato descartado.
Patron UX: Color semantico de estado (Tinder, apps de swipe)
Bloque 4 — Spinner en CandidatoPosturas
Problema: Text "Cargando..." en lugar de Spinner
Cambio: Reemplazar el Text por <Spinner size="large" /> centrado en una View, mismo patron que el loading de DetalleCandidatoScreen propio.
Beneficio: Consistencia de loading states en toda la app.
Patron UX: Consistent feedback (Nielsen #1)
Bloque 5 — Hint condicional a existencia de justificacion
Problema: "Toca para ver justificacion" aunque no haya justificacion
Cambio: Condicionar el hint a si p.justificacion != null. Si no hay justificacion, no mostrar hint. Si hay justificacion, mostrar el hint.
Beneficio: Sin feedback false, sin taps que no hacen nada visible.
Patron UX: Visibility of system status (Nielsen #1)
Bloque 6 — buildShareText usa formatMatchPercentage
Problema: Inconsistencia potencial entre UI y texto compartido
Cambio: Reemplazar `${Math.round(matchPct)}%` por `formatMatchPercentage(matchPct)` en buildShareText.
Beneficio: Unica fuente de verdad para el formato del porcentaje.
Patron: DRY — un solo punto de formato

Regla de contraste — hero background (valores reales del tema):

Light mode → c.primary = #2E5F7E (azul oscuro). Texto blanco encima: ratio 5.5:1 → AA pasa.
Dark mode → c.primary = #7BB5D4 (azul claro). Texto blanco encima: ratio 2.2:1 → AA falla.

Dos consecuencias directas:
1. El 87% en verde sobre el hero azul falla en ambos modos — verde sobre azul nunca da 4.5:1. Fix aplicado en estos mockups: usar blanco.
2. Nuestra propuesta de usar c.primary como hero background tiene un problema en dark mode: texto blanco sobre #7BB5D4 no es accesible.

Fix correcto para dark mode: usar primary800 = #1B3D53 como fondo del hero en dark mode (azul muy oscuro, texto blanco da ratio ~10:1), o detectar el modo y aplicar texto oscuro (#0E1E2A) sobre el azul claro.
En la implementacion: const heroBg = isDark ? c.primary800 : c.primary;

El 87% grande en el MatchBlock (fuera del hero, sobre c.bg neutro) si puede ser verde — ahi contrasta correctamente.
Fase 11 · Justificacion UX / UI
Hero con c.primary en lugar de c.accent2
Problema: token de hover usado en fondo institutcional
Beneficio: cumple DS-11 P6, da seriedad
Patron UX: Institutional hero (LinkedIn, apps civicas)
Friccion eliminada: incoherencia semantica del sistema de tokens
Metrica: +confianza institucional percibida
"Ver todas las posturas →" en ResumenTab
Problema: el usuario no sabe que hay mas posturas
Beneficio: la tab Posturas se descubre sin explorar
Patron UX: Progressive disclosure (Spotify, Airbnb)
Friccion eliminada: abandono por no saber que existe la tab
Metrica: +clicks a la tab Posturas, +tiempo en pantalla
Descartar activo con fondo danger
Problema: X activo con fondo azul (positivo)
Beneficio: el usuario entiende el estado sin leer
Patron UX: Estado visual semantico (Tinder)
Friccion eliminada: confusion sobre si el candidato esta descartado
Metrica: -taps accidentales de "des-descartar"
Spinner en CandidatoPosturas
Problema: Text plano donde todo usa Spinner
Beneficio: consistencia de feedback en toda la app
Patron UX: Consistency and standards (Nielsen #4)
Friccion eliminada: percepcion de estado de error vs carga
Metrica: +percepcion de calidad de la app
Hint condicional a justificacion existente
Problema: "Toca para ver" sin contenido disponible
Beneficio: sin feedback falso, sin taps vacios
Patron UX: Visibility of system status (Nielsen #1)
Friccion eliminada: confusion "es un bug?" cuando nada pasa
Metrica: -frustration signals
buildShareText usa formatMatchPercentage
Problema: Math.round() puede diferir de la UI
Beneficio: unica fuente de formato del porcentaje
Patron: DRY (Don't Repeat Yourself)
Friccion eliminada: inconsistencia entre lo que se ve y lo que se comparte
Metrica: +credibilidad en el texto compartido
Fase 12 · Impacto Esperado
Confianza institucional
Antes: fondo accent2 (hover state)
Despues: fondo primary — seriedad y consistencia
Exploracion de posturas
Antes: tab Posturas descubierta por azar
Despues: CTA explicito en ResumenTab
Claridad de estado
Antes: X descartado = azul (positivo)
Despues: X descartado = rojo (danger)
Consistencia de loading
Antes: Text plano en CandidatoPosturas
Despues: Spinner consistente con el resto
Feedback correcto en posturas
Antes: hint aparece sin justificacion
Despues: hint solo si hay justificacion
Cumplimiento DS-11
Antes: 3 tokens incorrectos (accent2, info badge, primary solid)
Despues: primary, neutral badge, danger solid
