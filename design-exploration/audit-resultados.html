Fase 1 · Componentes Frontend
useEffect con eslint-disable -- mutaciones sin deps
ResultadosScreen.tsx L194-204
Stale closure / Deuda lint
Problema
El useEffect que dispara authMutation.mutate() / guestMutation.mutate() tiene eslint-disable para suprimir deps faltantes. El array real incluye solo [tipoEleccionId, isGuest, esTipoBase] pero omite las funciones mutate y getRespuestasParaAnonimo
En React Query, las funciones mutate son tecnicamente estables entre renders. Pero suprimir el lint sin documentarlo crea deuda de mantenimiento invisible
Fix correcto
Opcion A: Reemplazar el eslint-disable por un comentario que explique explicitamente: "// mutate es estable en React Query (referencia: RQ docs #stable-values)"
Opcion B: Usar useRef para las mutaciones y leerlas desde el ref dentro del effect -- rompe la dependencia sin suprimir el lint
AppShell active="home" -- sin tab "resultados" en el BottomNav
ResultadosScreen.tsx L330, L348, L379
UX / Orientacion de tab
Contexto
AppTab = "home"|"candidatos"|"comparar"|"noticias"|"config" -- no existe "resultados". ResultadosScreen usa active="home" resaltando el tab Home mientras el usuario ve resultados
MisGuardados, MisRespuestas, PerfilScreen usan active={null}. GestionEleccionesScreen fue corregida de active="home" a active={null} (BUG-020)
Debate
active="home": defensible -- Resultados es parte del flujo Home. Orientacion contextual
active={null}: mas honesto semanticamente. Consistente con el patron del resto de screens secundarios
esTipoBase desde useTiposEleccion() -- tercer screen con el patron fragil
ResultadosScreen + CuestionarioScreen + SubmitDoneScreen
Patron x3 -- ampliar BUG-026
Impacto en Resultados
Si useTiposEleccion() no resolvio cuando el useEffect del match se ejecuta, esTipoBase = false. El effect dispara authMutation.mutate() para un tipo base -- el backend responde 400. El error se silencia, pero el flujo queda en estado inconsistente con spinner indefinido
Solucion
Ampliar BUG-026: guardar esTipoBase en el store al llamar loadForTipoEleccion(). Un cambio elimina useTiposEleccion() de los tres screens donde solo se usaba para este calculo
Fase 2 · Auditoria UX / UI
UX
Grid responsive y cardFlexBasis correctos. La logica de 1/2/3/4 columnas con breakpoints documentados y cardFlexBasis calculado fuera del map (no N veces) es el patron correcto para listas de alta densidad.
Contexto de ubicacion y cobertura claro. La card de aviso para !comunaUsuario con CTA directo, y la card neutral cuando hay comuna configurada, son UX honesto. El usuario siempre sabe por que ve (o no ve) ciertos candidatos.
Filtro por partido sin CTA reset cuando result = 0. Cuando todos los candidatos de un partido estan descartados, el usuario ve el empty state sin boton de salida. Nielsen #5: siempre dar una salida clara.
Banner TENTATIVA sin orientacion accionable. El banner dice que el match es tentativo pero no dice cuantas preguntas mas mejorarían la precision. "Responde X preguntas mas" seria accionable.
UI / DS
getMatchColor usado de forma consistente. topColor y scoreCol ambos via getMatchColor -- sin calculos duplicados en el JSX. El issue de 3 vs 5 tiers (TASK-009) es upstream de esta pantalla.
AppShell active="home" mientras se ven resultados. La tab Home permanece resaltada. Si el usuario llego desde una notificacion o deep link (no desde el flujo Home), la orientacion es incorrecta.
handleCtaTipoBase sin loading state. El CTA en el guardia de tipo base awaita loadForTipoEleccion() sin feedback. Mismo bug que BUG-029 en SubmitDoneScreen.

Fase 4 · Problemas Detectados
Critico
P-C01 · useEffect mutacion con eslint-disable -- deuda de mantenimiento sin documentacion
El useEffect del calculo del match suprime react-hooks/exhaustive-deps sin explicar por que. Las funciones mutate de React Query son estables, pero un developer futuro puede no saberlo y agregar dependencias incorrectas o romper el comportamiento.
ResultadosScreen.tsx L202: // eslint-disable-next-line react-hooks/exhaustive-deps | deps: [tipoEleccionId, isGuest, esTipoBase]
Alto
P-A01 · esTipoBase desde useTiposEleccion() -- tercer screen, amplia BUG-026
Si la query no resolvio, esTipoBase=false. El useEffect dispara el fetch de match para un tipo base. El backend responde 400. El error se silencia pero el estado queda inconsistente. La solucion de BUG-026 (esTipoBase en el store) resuelve los tres screens a la vez.
Medio
P-M01 · AppShell active="home" en pantalla sin tab propia
No existe tab "resultados". El patron correcto para screens secundarios sin tab propia es active={null} (MisGuardados, MisRespuestas, PerfilScreen). Usar active="home" resalta la tab Home mientras el usuario esta en Resultados.
P-M02 · handleCtaTipoBase async sin loading state -- doble-press posible
Mismo bug que BUG-029 en SubmitDoneScreen. El CTA del guardia esTipoBase awaita loadForTipoEleccion() sin feedback visual ni disabled. Button ya tiene loading y disabled props.
P-M03 · Filtro partido sin CTA reset cuando filteredResults = 0
El usuario que filtra por un partido y tiene todos sus candidatos descartados ve el empty state sin boton para volver a "Todos". Nielsen #5: dar siempre una salida clara.
Bajo
P-L01 · handleToggleFav, handleToggleDesc, goToDetalle sin useCallback
Se pasan como props a N instancias de RankingCard. Cada render de ResultadosScreen (ej. al cambiar el filtro) recrea estos handlers y causa re-render de todos los RankingCard.
P-L02 · Banner TENTATIVA sin orientacion accionable de cuantas preguntas faltan
P-L03 · styles en useMemo([c]) -- patron recurrente
