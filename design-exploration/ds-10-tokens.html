React Usage Guidelines

Patrones correctos e incorrectos para consumir tokens en componentes React Native / Expo.

Buenas practicas
CORRECTO
// Importar desde dimensiones.ts para colores de eje
import { getDimensionColors } from '../../domain/dimensiones';
const colors = getDimensionColors('economico', isDark);
<View style={{ borderLeftColor: colors.border }} />

// Usar useThemeColors() para tokens de UI
const c = useThemeColors();
<View style={{ backgroundColor: c.bg }} />

// Tier de afinidad centralizado — nunca inline
function getAffinityColor(pct: number): string {
  if (pct >= 81) return '#3A9E7A'; // --color-affinity-5
  if (pct >= 61) return '#6B9B7A'; // --color-affinity-4
  if (pct >= 41) return '#C89B5C'; // --color-affinity-3
  if (pct >= 21) return '#D07777'; // --color-affinity-2
  return '#B85C5C';                // --color-affinity-1
}
Anti-patrones
EVITAR
// MAL: hardcodear un color de eje
<View style={{ borderColor: '#0E7490' }} />
// BIEN: importar desde dimensiones.ts
const c = getDimensionColors('economico', isDark);

// MAL: usar el accent en el cuestionario
<Pressable style={{ backgroundColor: '#3A9E7A' }}>Siguiente</Pressable>
// BIEN: usar primary en cuestionario, accent SOLO en home
<Pressable style={{ backgroundColor: c.primary }}>Siguiente</Pressable>

// MAL: aplicar color de serie de datos al nombre del candidato
<Text style={{ color: '#3A9E7A' }}>{candidato.nombre}</Text>
// BIEN: el nombre siempre en color de texto
<Text style={{ color: c.text }}>{candidato.nombre}</Text>

// MAL: mezclar los tres verdes en el mismo viewport
// secondary (#7BA098) + success (#6B9B7A) + accent (#3A9E7A) = confusion
// BIEN: maximo 2 verdes por pantalla, roles inequivocos

// MAL: primary-light como texto sobre fondo claro
<Text style={{ color: '#4A9BBF' }}>Texto importante</Text> // 2.7:1 FAIL
// BIEN: primary-light solo sobre fondos oscuros (#1C3A52)
D

Reglas de Implementacion

Diez reglas no negociables que protegen la coherencia visual y la integridad del sistema.

1
El accent verde (#3A9E7A) esta PROHIBIDO en el cuestionario
Riesgo de sesgo: verde implica respuesta correcta. El cuestionario debe ser perceptualmente neutro.
critico
2
Los tokens de eje siempre vienen de dimensiones.ts
Son invariantes conceptuales; un rebrand de marca no los toca. La capa de dominio no hereda del sistema de color.
3
El orden de series de datos (S1–S5) es fijo entre pantallas
La leyenda mental del usuario se rompe si el mismo candidato aparece en colores distintos en el ranking vs. el comparador.
4
primary-light (#4A9BBF) solo sobre fondos oscuros
Contraste 2.7:1 sobre --color-surface-bg — falla WCAG 2.2 AA. Reservado para textos sobre --color-brand-hero.
WCAG
5
brand-hero (#1C3A52) max 40% del viewport en flujos largos
Fatiga visual documentada en sesiones de cuestionario de mas de 10 preguntas sobre fondos muy oscuros.
6
Los tres verdes no coexisten en el mismo viewport
secondary + success + accent = ambiguedad irresolvible para el usuario. Max 2 roles de verde por pantalla.
7
Todo token de afinidad usa --color-affinity-N, nunca hex directo
Permite rebrand del sistema de afinidad sin buscar todos los componentes que usan el color.
8
Contraste minimo: texto normal 4.5:1 · texto grande 3.0:1 · UI 3.0:1
WCAG 2.2 AA obligatorio. Verificar con herramienta automatica en CI antes de merge.
WCAG
9
El color del tier NUNCA se aplica al nombre del candidato
El nombre es dato; el tier es estado del match. Mezclarlos implica que "verde = candidato bueno" — sesgo de framing.
critico
10
Nuevos ejes requieren test WCAG antes de merge
El test en dimensiones.test.ts blinda la accesibilidad automaticamente. Sin test de contraste = PR bloqueado.
