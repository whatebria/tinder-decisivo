Fase 1 · Auditoria de Componentes Frontend
SubmitDoneScreen -- root View sin SafeAreaView
screens/SubmitDoneScreen.tsx L70 -- unico post-auth screen sin safe area
Critico -- contenido clippeado
El problema
El root es un View con flex:1 + justifyContent:center. Sin SafeAreaView, en iPhone con notch el heading "Listo!" puede quedar parcialmente tapado en la zona del status bar. En dispositivos con barra de gestos (iPhone home indicator, Android gesture nav), "Volver al inicio" puede quedar clippeado por debajo
ScreenChrome ya encapsula SafeAreaView con edges=["top"] por defecto. Es el wrapper correcto para screens post-auth full-focus sin bottom nav
Fix
Envolver ambos returns con ScreenChrome. Para este screen (centrado verticalmente, sin scroll), usar edges={["top","bottom"]} para proteger tanto el notch como el home indicator
Login y Register tambien tienen safe area parcial via el native stack header, pero SubmitDone no tiene header visible — cero proteccion en el top
handleCtaBase -- async sin loading state
SubmitDoneScreen.tsx L60-75
Doble-press posible
Problema
handleCtaBase awaits loadForTipoEleccion() sin feedback visual ni disabled state. El usuario puede presionar el CTA multiples veces durante el await, disparando llamadas concurrentes a la API
El Button DS ya tiene prop loading y disabled -- solo falta agregar el estado local
Catch sin feedback
El catch esta vacio intencionalmente (fail-safe: navegar siempre). Pero el usuario no sabe que algo fallo. Una alternativa: toast.error discreto + continuar navegando
Dos returns con JSX casi identico
SubmitDoneScreen.tsx L95-135
DRY menor
Duplicacion
Ambos modos comparten: Heading "Listo!", styles.root, y Link "Volver al inicio". Solo difieren el lead text, el subtle text, el label del CTA y el handler. Son 5-6 lineas duplicadas
Solucion
Un unico return con los valores derivados antes del return: leadText, subtleText, ctaLabel, onCta

Fase 2 · Auditoria UX / UI Profunda
UX
Celebracion apropiada. El Heading verde "Listo!" en color success es la recompensa emocional correcta despues de completar el cuestionario. No es exagerado ni usa confetti — apropiado para una app civica.
Sin loading en handleCtaBase. El usuario presiona "Ver mis matches en Presidenciales" y nada pasa visualmente durante el await. La sensacion es que la app no responde. El Button del DS tiene loading prop — es un cambio de 5 lineas.
Sin feedback de error en handleCtaBase. Si loadForTipoEleccion falla, el catch navega en silencio. El usuario llega a Resultados sin los datos del tipo especifico cargados — puede ver resultados incompletos sin entender por que.
primeraEspecificaActiva = null si tipos no cargaron. Si el usuario llega a SubmitDone con useTiposEleccion() aun en loading, ve el CTA "Activar una eleccion" en lugar de "Ver mis matches en X". Premia al usuario lento de red con un CTA de menor valor.
UI / Safe Area
Sin ScreenChrome -- contenido clippeado en notch. El root es un View raw. En iPhone 14 Pro (47px de notch) el "Listo!" puede quedar parcialmente tapado. En Android con gesture nav, "Volver al inicio" puede quedar bajo la barra de gestos. Es el unico screen post-auth sin ninguna proteccion.
Copy correcto y diferenciado por modo. "Guardamos tus respuestas generales" (base) vs "Guardamos tus respuestas" (eleccion) es una distincion semantica correcta. El usuario sabe que tipo de respuestas guardo.
Sin accessibilityLiveRegion en el heading de exito. Cuando el usuario llega a esta pantalla, VoiceOver deberia anunciar automaticamente "Listo!" sin que tenga que explorar el contenido. accessibilityLiveRegion="assertive" en el Heading lo conseguiria.

Fase 4 · Problemas Detectados
Critico
P-C01 · Sin SafeAreaView ni ScreenChrome -- contenido clippeado en notch y gesture bar
SubmitDoneScreen es el unico screen post-auth de toda la app que renderiza un View raw sin ninguna proteccion de safe area. En iPhone 14 Pro (notch de 47px), el Heading "Listo!" puede quedar tapado por el notch. En Android con gesture nav, "Volver al inicio" puede quedar bajo la barra de gestos del sistema. CuestionarioScreen y DetalleCandidatoScreen usan ScreenChrome correctamente. Esta pantalla lo omitio.
SubmitDoneScreen.tsx L70: return (<View style={styles.root}>) -- sin ScreenChrome, sin SafeAreaView, sin useSafeAreaInsets
Medio
P-M01 · handleCtaBase async sin loading state ni disabled -- doble-press posible
Durante el await de loadForTipoEleccion(), el CTA permanece activo y sin feedback. El usuario puede presionar multiples veces. Button del DS tiene loading y disabled props.
SubmitDoneScreen.tsx L60-75: async function handleCtaBase() -- sin useState(isLoading)
P-M02 · handleCtaBase catch vacio -- usuario navega a Resultados con posible estado incompleto sin saberlo
Si loadForTipoEleccion falla, la navegacion ocurre sin que el usuario sepa que los datos del tipo no se cargaron. Resultados puede mostrar datos incompletos o del tipo anterior. Un toast discreto antes de navegar informaria al usuario sin bloquear el flujo.
SubmitDoneScreen.tsx L67-71: catch { /* Fail-safe */ } -- sin toast ni log
P-M03 · primeraEspecificaActiva depende de useTiposEleccion() en loading -- CTA incorrecto si tipos no estan cargados
Si el usuario llega a SubmitDone antes de que useTiposEleccion() resuelva (cache vacio, red lenta), primeraEspecificaActiva = null y el CTA muestra "Activar una eleccion" en lugar de "Ver mis matches en X". El usuario recibe un CTA de menor valor por culpa de latencia de red.
P-M04 · Dos returns con JSX casi identico -- DRY menor
Ambos modos comparten Heading "Listo!", styles.root, y Link "Volver al inicio". Solo difieren lead text, subtle text, ctaLabel y onCta. Un unico return con derivados pre-calculados elimina la duplicacion.

P-L02 · handleVolver, handleCtaEleccion, handleCtaBase sin useCallback

Fase 11 · Justificacion
ScreenChrome (critico)
Todos los screens post-auth full-focus usan ScreenChrome. Este es el unico que lo omite. Es un olvido, no una decision.
Loading en CTA base
El DS ya tiene Button loading prop. 5 lineas de codigo, elimina el riesgo de doble-press y da feedback claro al usuario.
Un unico return (DRY)
Reduce el surface de bugs: si el copy cambia, se cambia en un solo lugar. Con 4 derivados pre-calculados el codigo queda mas facil de leer.
accessibilityLiveRegion
WCAG 4.1.3 (Status Messages). Un usuario de VoiceOver que completa el cuestionario y llega a esta pantalla necesita saber automaticamente que tuvo exito sin explorar la pantalla manualmente.
