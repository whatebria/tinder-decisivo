Fase 1 · Auditoria de Componentes Frontend
QuestionCard
organisms/QuestionCard.tsx · 4.2 KB · NO se usa en ninguna pantalla de produccion
Dead code / YAGNI
Hallazgo
QuestionCard NO aparece en ningun import de screens/*.tsx. Solo en QuestionCard.showcase.tsx (DS catalog) y en index.generated.ts (auto-generado). El JSDoc dice "corazon del cuestionario" -- engañoso para developers futuros que podrian asumir que es el componente oficial
Tiene su propio footer con botones Volver/Siguiente y RadioGroup, duplicando la implementacion del cuestionario real con una API diferente
Riesgo y solucion
Un developer futuro podria encontrar QuestionCard y usarlo "porque es el corazon del cuestionario", introduciendo regresiones
Agregar @deprecated JSDoc y eliminar en sprint de limpieza. O eliminar directamente si no hay plan de reutilizacion
CuestionarioHeader
organisms/CuestionarioHeader.tsx · Excelente
Solo un detalle menor
Fortalezas
Fondo fijo #2E5F7E -- identidad de "modo concentrado", independiente del tema
WCAG documentado en JSDoc: #FFF/#2E5F7E = 5.5:1 (AA)

Progressbar con accessibilityRole="progressbar" y accessibilityValue

Unico problema
styles en useMemo([]) con deps vacías: funcionalmente igual a nivel de modulo, pero con overhead de useMemo. Deberia ser StyleSheet.create a nivel de modulo
handleSubmit + handleSelectRespuesta
CuestionarioScreen.tsx L191-213
Sin useCallback
Impacto
handleSelectRespuesta: pasada como onChange a RadioGroup. Se recrea en cada render. El cuestionario re-renderiza en cada seleccion de respuesta o peso -- alta frecuencia de renders
handleSubmit: pasada a dos Buttons (Enviar y Ver resultados parciales). Referencias inestables
scrollToTop inline
scrollToTop y la funcion de scroll-to-bottom son lambdas inline en onPress. Se recrean en cada render aunque nunca cambian su implementacion
esTipoBase -- dependencia en query asyncrona
CuestionarioScreen.tsx L89-95
Ruta incorrecta potencial
Problema
Si useTiposEleccion() aun no resolvio cuando el usuario llega al cuestionario, esTipoBase = false por defecto. El submit navega a SubmitDone con mode="eleccion" cuando deberia ser mode="base"
Solucion
Guardar es_base en el store de cuestionario cuando se llama a loadForTipoEleccion(). El store ya tiene tipoEleccionId -- agregar esTipoBase junto
Fase 2 · Auditoria UX / UI Profunda
UX
Flujo una-pregunta-por-vez excelente. Header sticky, footer sticky, scroll automatico al seleccionar opcion, "No se" semanticamente separada. La arquitectura del cuestionario es de referencia para el proyecto.
Chips de peso sin valor por defecto visible. Al seleccionar una opcion Likert, los chips aparecen todos sin seleccionar visualmente aunque DEFAULT_PESO=2 ya esta aplicado en el store. El usuario no sabe si tiene que elegir un peso o si ya hay uno.
"Ver resultados parciales" usa el mismo handler que "Enviar". Semanticamente podrian diferenciarse (submit parcial vs submit final), pero en la implementacion actual hacen exactamente lo mismo. El boton es ghost style -- menos prominente, lo que es correcto.
UI / Design System
CuestionarioHeader: implementacion de referencia. El fondo fijo #2E5F7E, los colores sobre hero sin depender del tema, el progressbar accesible. Patron que HomeHeroSection ya sigue.
ejeLabel usa c.primary (azul) para todos los ejes. DS-08 define getDimensionColors(key) para mostrar el color correcto por eje semantico. Alinear el cuestionario con el radar chart de DetalleCandidato mejoraria la coherencia visual de la app.
Chips de peso sin accessibilityHint contextual. accessibilityLabel="Peso: Medio" no comunica que "Medio" se refiere a la importancia de la pregunta para el match. Un usuario de VoiceOver podria confundirlo con una opcion de respuesta.
Fase 3 · Benchmarking
Typeform
Una pregunta por vez, scroll automatico
El patron de Typeform es exactamente lo que implementa CuestionarioScreen. El scroll automatico al seleccionar es la misma mecanica del setTimeout de 150ms.
El patron actual es correcto y de nivel Typeform.
Duolingo
Valor por defecto visible en preferencias
Cuando Duolingo pide una preferencia adicional, siempre muestra el valor por defecto ya seleccionado para que el usuario sepa que puede cambiar o dejar el sugerido.
Los chips de peso deberian mostrar DEFAULT_PESO=2 ("Medio") activo desde el principio.
16Personalities
Contexto de importancia siempre visible
El selector de importancia tiene siempre el texto "Esta pregunta es importante para mi" como contexto claro sobre que se esta evaluando.
accessibilityHint="Importancia de este tema para tu compatibilidad con los candidatos" en los chips de peso.
SurveyMonkey
Indicador de preguntas sin responder
Si el usuario omite una pregunta y salta a la siguiente, SurveyMonkey muestra un indicador de que hay preguntas pendientes antes de enviar.
El actual canSubmit=puedeEnviar() ya valida todas -- el patron es correcto. Solo falta un indicador visual de cuales quedan sin responder si el usuario volvio atras.
Fase 4 · Problemas Detectados
Alto
P-A01 · QuestionCard.tsx es dead code en produccion -- solo en DS catalog showcase
4.2 KB de componente que CuestionarioScreen no usa. El JSDoc "corazon del cuestionario" es engañoso. Tiene botones y RadioGroup propios que duplican la implementacion real con una API diferente. Mantenerlo sin @deprecated crea confusion para developers futuros.
grep QuestionCard en screens/*.tsx: 0 resultados. Solo en showcase + index.generated.ts
P-A02 · handleSubmit y handleSelectRespuesta sin useCallback
handleSelectRespuesta se recrea en cada render y se pasa a RadioGroup. El cuestionario re-renderiza en cada interaccion del usuario (cada respuesta, cada peso). handleSubmit se pasa a dos Buttons. Referencias inestables en la pantalla mas interactiva del flujo.
CuestionarioScreen.tsx L191: async function handleSubmit() | L205: function handleSelectRespuesta()
Medio
P-M01 · esTipoBase depende de query useTiposEleccion() -- puede no estar lista al submit
Si useTiposEleccion() aun esta cargando cuando el usuario llega al cuestionario, esTipoBase = false. El submit navega a SubmitDone con mode incorrecto. Solucion: guardar es_base en el store cuando se llama a loadForTipoEleccion().
CuestionarioScreen.tsx L89-95: const esTipoBase = useMemo(() => tipos.find(t => t.id === tipoEleccionId)?.es_base ?? false, [tipos, tipoEleccionId])
P-M02 · Chips de peso aparecen sin DEFAULT_PESO visible aunque ya esta aplicado en el store
DEFAULT_PESO=2 se aplica en el store cuando el usuario selecciona una opcion, pero los chips se muestran todos sin seleccionar visualmente. El usuario no sabe si debe elegir un peso.
P-M03 · ejeLabel usa c.primary para todos los ejes (DS-08 especifica color por eje)
El label del eje tematico ("ECONOMIA", "SOCIEDAD") usa c.primary (azul) siempre. DS-08 define getDimensionColors(key, isDark) para el color semantico por eje. Aplicarlo alinearia el cuestionario con el radar chart de DetalleCandidato.
CuestionarioScreen.tsx L113: ejeLabel: { ...typography.overline, fontWeight: "700", color: c.primary }
Bajo
P-L01 · CuestionarioHeader styles en useMemo([]) -- deberia ser modulo-level
CuestionarioHeader.tsx L77: const styles = useMemo(() => StyleSheet.create({...}), []);
P-L02 · Chips de peso sin accessibilityHint del contexto ("importancia para el match")
accessibilityLabel="Peso: Medio" no comunica que se refiere a la importancia de la pregunta. Un usuario de VoiceOver podria confundirlo con una opcion de respuesta.
P-L03 · CuestionarioScreen styles en useMemo([c, insets.bottom])
Mismo patron ineficiente recurrente en la app.
Fase 5 · Propuesta
Bloque 1 — Deprecar QuestionCard
Cambio: Agregar @deprecated al JSDoc: "No se usa en produccion. Ver CuestionarioScreen para el patron actual." Eliminar en sprint de limpieza.
Beneficio: developers futuros no se confunden.
Bloque 2 — useCallback en handlers
Cambio: handleSubmit y handleSelectRespuesta como useCallback con deps correctas.
Beneficio: referencias estables en RadioGroup y Buttons, sin re-renders cascada.
Bloque 3 — esTipoBase en el store
Cambio: Agregar esTipoBase: boolean al store. Setearlo en loadForTipoEleccion().
Beneficio: modo de SubmitDone siempre correcto sin dependencia de query asyncrona.
Bloque 4 — DEFAULT_PESO visible en chips
Cambio: El chip con value === respuesta.peso (que ya tiene DEFAULT_PESO desde el store) aparece activo desde el principio.
Beneficio: visibilidad del sistema (Nielsen #1).
