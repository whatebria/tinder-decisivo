MisGuardadosScreen — Mis Guardados

El hallazgo critico es una UI enganosa: los chips de filtro por eleccion se renderizan, se pueden activar y tienen estado visual, pero NO filtran los datos. El comentario del propio codigo lo documenta como TODO. Ademas, los toggles de posturas y noticias fallan silenciosamente sin onSuccess/onError, y hay 8 queries activas simultaneamente aunque el usuario solo este mirando un tab.

Fase 1 · Auditoria de Componentes Frontend
Filtro por eleccion (chips)
MisGuardadosScreen.tsx L275-300 -- eleccionFilter sin efecto en datos
UI enganosa
El problema
eleccionFilter se actualiza en estado cuando el usuario toca un chip, pero NINGUN render function (renderFavoritos, renderDescartados, renderPosturas) usa eleccionFilter para filtrar los datos. El comentario del codigo lo documenta: "Por ahora solo 'Todas' tiene efecto; el filtrado por tipo de eleccion queda como TODO"
Los chips de tipo de eleccion aparecen activos (fondo primary) cuando se seleccionan, dando feedback visual de que estan filtrando. El usuario espera ver menos items y sigue viendo todos
Opciones
Opcion A (recomendada): Ocultar los chips de tipo de eleccion hasta implementar el filtrado. Solo mostrar "Todas" o no mostrar el filtro
Opcion B: Implementar el filtrado -- requiere que los bookmarks expongan el tipo de eleccion del candidato (verificar con el backend)
renderPosturas / renderNoticias -- mutaciones sin feedback
MisGuardadosScreen.tsx L243 / L268
Falla silenciosa
Problema
togglePos.mutate(b.postura) -- sin onSuccess ni onError. Si la llamada falla, el usuario no lo sabe. Contraste con handleQuitarFav que si tiene callbacks de toast
toggleNot.mutate(b.noticia) -- mismo problema. El usuario puede quitar el bookmark de una noticia y si falla, no recibe ningun feedback
Solucion
Agregar handleQuitarPostura y handleQuitarNoticia como funciones memoizadas con callbacks de toast, igual al patron de handleQuitarFav y handleRestoreDesc
renderCandidatoCard + initials -- DRY y memoizacion
MisGuardadosScreen.tsx L164-210
DRY + Performance
Problemas
initials() es un wrapper de una linea de iniciales() que ya esta importado. DRY violation: funcion innecesaria que oscurece la dependencia real
renderCandidatoCard captura c, styles, navigation en closure sin useCallback. Se recrea en cada render, causando re-render de todos los hijos
handleQuitarFav y handleRestoreDesc sin useCallback
Solucion
Eliminar la funcion initials() local y llamar iniciales() directamente
Convertir renderCandidatoCard en un componente React memoizado (React.memo) para evitar re-renders innecesarios
8 queries activas + currentBody como IIFE
MisGuardadosScreen.tsx L88-108 / L321-330
Performance + Legibilidad
8 queries simultáneas
useFavoritos, useDescartados, usePosturasBookmarks, useNoticiasBookmarks se activan al montar el componente, aunque el usuario solo este viendo la tab "Favoritos". Para listas largas esto puede generar carga innecesaria en el backend
Las queries de mutations (toggle*) son necesarias siempre, pero las 4 queries de datos podrian ser lazy (enabled segun la tab activa)
IIFE currentBody
const currentBody = (() => { switch(tab) {...} })() es un patron poco idiomatico en React. Mejor: una funcion named renderBody() o un objeto de renderFns[tab]
Posturas card -- jerarquia visual del candidato
MisGuardadosScreen.tsx L218-250
UX / Legibilidad
Problema
El nombre del candidato se muestra en cardMeta (overline, c.textSecondary) -- visualmente secundario. El texto de la pregunta esta en cardTitle (prominente). Para el usuario que guarda posturas de varios candidatos, el "de quien es esta postura" queda relegado
Propuesta
Mostrar el candidato primero con Avatar + nombre en texto primario. La pregunta y la respuesta en segundo nivel. Mismo patron que las cards de favoritos/descartados
Fase 2 · Auditoria UX / UI Profunda
UX
Filtro de elecciones enganoso: el usuario puede seleccionar una eleccion especifica en los chips, ver el chip activo (azul), y los datos no cambian. Es el tipo de bug mas dañino: no es un error visible, es una expectativa rota. El usuario asume que el filtro no encontro nada o que todos sus guardados son de esa eleccion.
Falla silenciosa en posturas y noticias: quitar una postura o noticia guardada no emite toast de confirmacion ni de error. Si la operacion falla en el backend, la card desaparece visualmente (optimistic) pero vuelve a aparecer en la proxima carga, sin que el usuario entienda por que.
Descartados sin contexto de por que fueron descartados: la tab "Descartados" muestra los candidatos con un boton "Restaurar". El usuario no ve cuando los descarto ni por que. Para tomar la decision de restaurar, necesitaria entrar al detalle del candidato.
Cand sin id -- Pressable silencioso: si `cand.id == null`, el Pressable tiene `accessibilityRole="button"` pero el onPress no hace nada. VoiceOver anuncia "Ver detalle de Candidato" como boton, el usuario lo activa, y nada ocurre. Sin feedback de que la accion no esta disponible.
UI / Design System
Posturas card: candidato visualmente secundario: el nombre del candidato aparece en overline muted sobre el texto de la pregunta. Para una lista de posturas de varios candidatos, el primero que debe captar la atencion visual es "de quien es", no "que pregunta".
Spacer View vacio en renderPosturas: `<View style={styles.row}><View /><BookmarkButton...` usa un View vacio para empujar el BookmarkButton a la derecha. Hack de layout que se puede reemplazar con `justifyContent: "flex-end"` en el row.
Tab Noticias condicionalmente oculta pero tipo en GuardadoTab: cuando SHOW_NOTICIAS=false, el tab no aparece pero el tipo "noticias" sigue existiendo en GuardadoTab. Si por alguna razon `tab` se establece como "noticias", el switch retorna null silenciosamente.
Fase 3 · Benchmarking
Pocket
Filtros claramente marcados como "en construccion"
Si una funcion de filtrado no esta disponible, Pocket la muestra en gris con tooltip "Proximamente". No da feedback visual de seleccion si no tiene efecto.
Adaptacion: ocultar los chips de eleccion o mostrarlos con opacity reducida + tooltip "Filtrado por eleccion disponible pronto".
Spotify (Liked Songs)
Feedback de guardado en tiempo real
Al quitar un guardado (unlike), aparece un toast "Eliminado de tu biblioteca" con un undo link. Si falla, el item vuelve y aparece un toast de error.
Adaptacion: agregar handleQuitarPostura y handleQuitarNoticia con toast de confirmacion, igual a handleQuitarFav.
Airbnb (Wishlists)
Card con jerarquia clara: imagen > nombre > detalle
El elemento principal (la propiedad) siempre es lo mas prominente visualmente. El nombre del anfitrion es secundario.
Adaptacion: en posturas, el candidato debe ser prominente (Avatar + nombre bold) y la postura en segundo nivel.
Feedly
Lazy loading por tab
Feedly solo carga el contenido de la seccion activa. Al cambiar de seccion, hace una nueva request. Evita cargar 4 endpoints cuando el usuario solo ve 1.
Adaptacion: activar las queries segun el tab activo con enabled: tab === "favoritos" para cada hook.
Twitter (Bookmarks)
Estado de descartado con contexto temporal
Los tweets silenciados muestran cuando fueron silenciados. El usuario puede evaluar si sigue siendo relevante la accion.
Adaptacion: mostrar la fecha de descarte en la card de descartados si el backend la expone. Permite tomar mejores decisiones al restaurar.
Fase 4 · Problemas Detectados
Critico
P-C01 · Filtro de elecciones con estado visual pero sin efecto en datos
Los chips de tipo de eleccion se pueden seleccionar y muestran el chip activo en azul, pero ningun render function usa el estado eleccionFilter para filtrar los datos. El usuario experimenta una expectativa rota: cree estar filtrando, pero ve todos sus guardados independientemente del chip seleccionado. Documentado como TODO en el propio codigo.
MisGuardadosScreen.tsx L19: "el filtrado por tipo de eleccion queda como TODO" | L115: setEleccionFilter sin uso en renderFavoritos/renderDescartados/renderPosturas
Alto
P-A01 · Mutaciones de posturas y noticias sin feedback de exito/error
togglePos.mutate(b.postura) y toggleNot.mutate(b.noticia) no tienen callbacks de onSuccess ni onError. Si la operacion falla, el item desaparece visualmente (UI optimista) y vuelve a aparecer en la proxima carga sin que el usuario entienda por que. Contrasta con handleQuitarFav y handleRestoreDesc que si tienen toasts.
MisGuardadosScreen.tsx L243: togglePos.mutate(b.postura) | L268: toggleNot.mutate(b.noticia)
P-A02 · initials() funcion local duplica iniciales() importado (DRY violation)
La funcion local initials(nombre, apellido) es un wrapper de una linea de iniciales({nombre, apellido}) que ya esta importado de utils/candidato. Agrega una capa de indirection innecesaria y duplica la dependencia de forma oscura. Viola DRY.
MisGuardadosScreen.tsx L162-164: function initials(nombre, apellido) { return iniciales({nombre, apellido}); }
P-A03 · 8 queries activas al montar -- sin lazy loading por tab
useFavoritos, useDescartados, usePosturasBookmarks, useNoticiasBookmarks se activan todas al montar el componente. El usuario que entra a ver sus Favoritos desencadena 4 requests de datos aunque solo vaya a usar 1. En conexiones lentas o con listas largas, esto aumenta el tiempo a primer contenido visible.
Medio
P-M01 · Posturas card: candidato en overline muted, pregunta prominente
En la card de postura guardada, el nombre del candidato aparece en cardMeta (typography.overline, c.textSecondary) y la pregunta en cardTitle (body bold, c.text). Para una lista de posturas de varios candidatos, el usuario necesita saber primero "de quien" antes de ver "que dijo". La jerarquia visual actual invierte la prioridad de informacion.
P-M02 · Pressable en renderCandidatoCard silencioso cuando cand.id == null
Si cand.id es null, el Pressable tiene accessibilityRole="button" pero su onPress es un no-op. VoiceOver anuncia el elemento como boton interactivo, el usuario lo activa, y nada ocurre. Sin feedback de que la accion no esta disponible (disabled, ni mensaje).
MisGuardadosScreen.tsx L185: cand.id != null && navigation.navigate(...) -- sin else
P-M03 · currentBody como IIFE -- patron poco idiomatico
La logica de seleccion de render function se implementa como una IIFE (Immediately Invoked Function Expression): const currentBody = (() => { switch(tab)... })(); Este patron es inusual en componentes React y dificulta la lectura.
MisGuardadosScreen.tsx L321: const currentBody = (() => { switch (tab) { ... } })()
Bajo
P-L01 · View vacio como spacer en renderPosturas
La fila de acciones en la card de postura usa <View /> vacio para empujar el BookmarkButton a la derecha. Se puede resolver con justifyContent: "flex-end" en el row style.
MisGuardadosScreen.tsx L246: <View style={styles.row}><View /><BookmarkButton...>
P-L02 · handleQuitarFav y handleRestoreDesc sin useCallback
Ambas funciones se recrean en cada render. Se pasan como props a componentes hijos dentro de renderCandidatoCard.
P-L03 · styles en useMemo([c]) -- patron ineficiente recurrente
Mismo problema documentado en otras pantallas. StyleSheet se regenera en cada cambio de tema.
Fase 5 · Propuesta de Rediseno
Bloque 1 — Ocultar chips hasta implementar filtrado
Problema: UI enganosa -- chips con estado visual sin efecto
Cambio: Ocultar el bloque de chips de eleccion hasta que el backend exponga el tipo de eleccion en todos los bookmarks y el filtrado este implementado. Mantener el estado y la logica en el codigo para la implementacion futura, solo ocultar la UI.
Beneficio: Sin expectativas rotas.
Alternativa: Si se quiere mantener visible, agregar una nota "(Proximamente)" junto al label "Eleccion".
Bloque 2 — Handlers con toast para posturas y noticias
Problema: togglePos y toggleNot sin feedback
Cambio: Extraer handleQuitarPostura y handleQuitarNoticia con el mismo patron que handleQuitarFav (mutate + onSuccess/onError callbacks).
Beneficio: Consistencia de feedback en toda la pantalla.
Patron: Error visibility (Nielsen #1)
Bloque 3 — Eliminar initials() wrapper
Problema: DRY violation -- wrapper de una linea
Cambio: Llamar iniciales() directamente en renderCandidatoCard.
Beneficio: Menos indirection, dependencia explicita.
Patron: DRY, YAGNI
Bloque 4 — Lazy loading por tab
Problema: 8 queries activas al montar
Cambio: Activar cada query segun el tab activo con la prop `enabled` de React Query:
`useFavoritos({ enabled: tab === "favoritos" })`
Beneficio: Solo se carga el tab visible. Menos requests, TTFCP menor.
Patron UX: Progressive loading (Feedly, Twitter)
Bloque 5 — Posturas card con candidato prominente
Problema: candidato en overline muted, pregunta en bold
Cambio: Usar renderCandidatoCard como base y agregar el texto de la postura debajo del nombre del candidato, en lugar de la card independiente actual.
Beneficio: El usuario sabe de quien es cada postura de un vistazo.
Bloque 6 — renderBody() en lugar de IIFE
Problema: IIFE poco idiomatico en React
Cambio: Reemplazar el IIFE por una funcion named:
`function renderBody() { switch(tab) {...} }`
Y llamar `{renderBody()}` en el JSX.
Beneficio: Legibilidad, patron idiomatico React.
