novedades useMemo -- eslint-disable stale closure
HomeScreen.tsx L208-238
Stale closure potencial
Problema
El useMemo de novedades usa iniciarCuestionario() internamente pero no la incluye en las dependencias. El comentario lo documenta con // eslint-disable-next-line. iniciarCuestionario captura loadForTipoEleccion, progresoByTipo y navigation en closure -- si cualquiera de estos cambia, el handler onCta del item de novedades apunta a la version stale de iniciarCuestionario
El workaround correcto: extraer iniciarCuestionario como useCallback con sus dependencias reales, y luego incluirla en las deps de novedades. El eslint-disable indica que el codigo sabe que hay un problema pero lo suprime en lugar de resolverlo
Riesgo real
El riesgo es bajo en la practica si los stores de Zustand son estables (references fijas). Pero es un patron fragil que puede romperse con refactors futuros
useNoticiasFeed -- siempre activo aunque SHOW_NOTICIAS=false
HomeScreen.tsx L103
Request desperdiciada
Problema
useNoticiasFeed() se llama siempre al montar HomeScreen, independientemente del valor de SHOW_NOTICIAS. Cuando SHOW_NOTICIAS=false, el array noticias se usa solo para construir los items de novedades, pero ese codigo tambien esta condicionado por SHOW_NOTICIAS -- por lo que la request es completamente inutil
Mismo patron que TASK-039 (SHOW_NOTICIAS dead code) pero aplicado a un hook que hace una request de red real
Solucion
const { data: noticias = [] } = useNoticiasFeed({ enabled: SHOW_NOTICIAS })

Fase 2 · Auditoria UX / UI Profunda
UX
HomeHeroSection: arquitectura UX excelente. El hero unificado (fondo #1C3A52 + saludo + ring + CTA) resuelve el patron "doble borde" del HomeTopBar anterior. El CTA adapta su label a 3 estados (Empezar / Continuar / Ver mis matches) -- comunicacion de estado contextual correcta. El CountdownPill motiva urgencia electoral.
HomeMatchLocked: patron tinder-reveal efectivo. El blur-canvas + overlay da la sensacion de que hay algo que ver, motivando al usuario a completar el cuestionario. El CTA "Continuar cuestionario" en el overlay es redundante con el del hero, pero en este contexto es correcto -- el usuario que llega hasta aca puede haber olvidado el CTA del hero.
MatchSummaryCard ancho fijo en layout vertical. La card tiene CARD_WIDTH=260. En un iPhone 14 (390px), la card ocupa 260px dejando 130px libres a la derecha -- visualmente parece una card a medio renderizar. En tablets o web es mas evidente. Si se van a mostrar multiples matches en lista vertical, la card deberia ser full-width.
Sin estado de error para tiposLoading=true pero error presente. El useEffect que muestra toast en caso de error es correcto, pero el spinner de carga se sigue mostrando si el error ocurre. El usuario ve un spinner indefinido con un toast de error -- no sabe si seguir esperando o si algo fallo definitivamente.
UI / Design System
Progress: DS-11 P1 correctamente implementado. HomeElectionItem usa c.secondary para "sin_empezar" (verde accent) y c.primary para "en_curso" (azul). El estado "completa" usa c.success para la barra. Tokenizacion correcta y consistente.
HomeElectionItem: border c.primary en estado "en_curso" no documentado en DS-11. Cuando el cuestionario esta en curso, la card tiene borderColor: c.primary. DS-11 P1 especifica la barra de progreso pero no el borde de la card. Es una decision local no respaldada por el spec.
emailPrefix computed inline con .split("@")[0]. La logica de extraer el prefijo del email ya existe en deriveDisplayName(). HomeScreen hace el split manualmente antes de llamar a la util -- la util deberia aceptar directamente el email.
HomeTrustSection: solo visible para usuarios sin cuestionario. Esto es correcto segun la especificacion (showTrust = !isGuest && mejoresMatches.length === 0 && heroProgress === 0). Pero si un usuario completo el cuestionario y luego lo reinicio, HomeTrustSection vuelve a aparecer -- puede parecer condescendiente para usuarios veteranos.

Fase 4 · Problemas Detectados
Critico
P-C01 · novedades useMemo usa iniciarCuestionario() sin incluirla en deps -- stale closure
El useMemo de novedades llama iniciarCuestionario() en el handler onCta, pero iniciarCuestionario no esta en las dependencias (hay un eslint-disable comentado). Si loadForTipoEleccion, navigation o progresoByTipo cambian, el onCta del item de novedades apunta a la version vieja. El fix correcto: extraer iniciarCuestionario como useCallback y agregarla a las deps del useMemo.
HomeScreen.tsx L234: // eslint-disable-next-line react-hooks/exhaustive-deps | novedades deps: [tiposActivos, activeId, noticias]
Alto
P-A01 · useNoticiasFeed() siempre activo aunque SHOW_NOTICIAS=false
useNoticiasFeed() se llama incondicionalmente en HomeScreen. Cuando SHOW_NOTICIAS=false, el resultado nunca se usa para renderizar nada visible. Es una request de red desperdiciada en cada mount del Home, que es la pantalla que el usuario ve mas frecuentemente.
HomeScreen.tsx L103: const { data: noticias = [] } = useNoticiasFeed(); -- sin condicion
P-A02 · iniciarCuestionario, handleHeroCta, handleConfirmReiniciar sin useCallback
Los tres handlers principales se recrean en cada render. iniciarCuestionario se pasa a N instancias de HomeElectionItem (como onEmpezar, onContinuar, onVerResultados) y a novedades. handleHeroCta se pasa al HomeHeroSection. Cada re-render de HomeScreen causa re-render de todos sus hijos.
P-A03 · Estado de error de tiposLoading: spinner infinito con toast
Cuando useTiposEleccion falla, el useEffect emite un toast pero la pantalla sigue mostrando el Spinner. El usuario ve un spinner que nunca resuelve con un toast de error que desaparece. Sin boton de retry visible.
HomeScreen.tsx L118-120: if (tiposLoading) return Spinner -- sin manejo de error en el return anticipado
Medio
P-M01 · MatchSummaryCard CARD_WIDTH=260 fijo en layout vertical
La MatchSummaryCard tiene width:260 fijo. En HomeScreen se usa en una lista vertical (View, no ScrollView horizontal). En una pantalla de 390px (iPhone 14), la card ocupa 260px dejando 130px sin usar a la derecha. Visualmente parece una card a medio renderizar.
MatchSummaryCard.tsx L80: const CARD_WIDTH = 260 -- sin flexGrow ni width:"100%"
P-M02 · emailPrefix computed inline duplica logica de deriveDisplayName
HomeScreen hace email.split("@")[0] manualmente antes de llamar a deriveDisplayName(emailPrefix). La util ya encapsula la logica -- deberia aceptar el email directamente para evitar el split duplicado.
HomeScreen.tsx L115-117: const emailPrefix = email ? email.split("@")[0] : null;
P-M03 · HomeElectionItem borde c.primary en estado "en_curso" no especificado en DS-11
Cuando el cuestionario esta en curso, la card tiene borderColor: c.primary. DS-11 P1 especifica la barra de progreso (secondary/primary) pero no el borde de la card. Es una decision local que no tiene respaldo en el spec.
HomeElectionItem.tsx L117: borderColor: estado === "en_curso" ? c.primary : c.border2
Bajo
P-L01 · HomeTrustSection reaparece al reiniciar cuestionario
showTrust = heroProgress === 0 && mejoresMatches.length === 0. Si un usuario veterano reinicia el cuestionario, HomeTrustSection reaparece. Para usuarios que ya conocen la app puede parecer condescendiente.
P-L02 · Trust items hardcodeados en HomeHeroSection JSX
"~15 min", "100% privado", "Datos SERVEL" son strings directamente en el JSX. Deberian ser constantes exportadas para facilitar cambios sin buscar en el JSX.
P-L03 · styles en useMemo en todos los componentes del Home
HomeScreen, HomeHeroSection, HomeElectionItem, HomeMatchLocked y MatchSummaryCard todos usan el patron StyleSheet.create dentro de useMemo. Es el patron ineficiente documentado en multiples pantallas anteriores.
Fase 5 · Propuesta de Rediseno
Bloque 1 — Fix stale closure + useCallback
Problema: iniciarCuestionario sin useCallback ni deps correctas
Cambio: Convertir iniciarCuestionario a useCallback([loadForTipoEleccion, progresoByTipo, navigation, isGuest, toast]), luego incluirla en las deps del useMemo de novedades. Eliminar el eslint-disable.
Beneficio: referencias estables, sin stale closure, cumple exhaustive-deps.
Bloque 2 — useNoticiasFeed condicionado
Problema: request de red siempre activa aunque SHOW_NOTICIAS=false
Cambio: useNoticiasFeed({ enabled: SHOW_NOTICIAS })
Beneficio: 0 requests de noticias mientras el feature flag este desactivado.
Bloque 3 — Error state para tiposLoading
Problema: spinner infinito cuando la request falla
Cambio: Agregar manejo de error al return anticipado de loading: si error es truthy, mostrar EmptyState con retry.
Beneficio: El usuario puede recuperarse de errores de red.
Bloque 4 — MatchSummaryCard full-width en Home
Problema: CARD_WIDTH=260 en layout vertical
Cambio: Agregar prop fullWidth?: boolean a MatchSummaryCard. Cuando fullWidth=true, width:"100%" en lugar de CARD_WIDTH. En HomeScreen pasar fullWidth.
Beneficio: card visual completa en Home.
