Panorama R2 EGTAI - los 8 sub-requisitos

R2 (Technical robustness and safety) es donde matchVote esta objetivamente mejor de lo que la tesis lo hacia parecer. La documentacion existe distribuida en docs/backend/, docs/frontend.md y docs/buenas-practicas.md - hay que consolidarla en un capitulo de la tesis.

R2.1

Placement verificado

Parcial

Enforced por codigo: import_posturas requiere URL de fuente + justificacion por cada postura. 72 posturas con confidence HIGH/MEDIUM/LOW en fixtures. Test test_importers.py con --dry-run. Falta auditor externo (limitante compartida con casi todo el corpus VAA).

R2.2

Robustez del algoritmo

Cumple

Determinista, sin randomness ni ML opaco. Tests unitarios PUROS en test_services_matching.py (no tocan DB), tests de integracion end-to-end en test_algoritmo_matching.py (12.8 KB, el mas grande). Escenarios: todos de acuerdo, todos en desacuerdo, mix, confianza, top candidatos.

R2.3

Testing automatizado

Cumple

25 archivos de tests con pytest-django. Fixtures compartidos (datos_pesados con 6 seeds via management commands). Cobertura backend robusta. Deuda: 0% frontend (planeada Sprint 10 con Jest + React Testing Library).

R2.4

Ataques adversarios

Parcial

Sin pentest formal ni Snyk. PERO defensas activas: anti-user-enumeration en password reset (ResetError generico), DRF Permission classes por endpoint (26 endpoints revisados), user-scoped querysets, HTTPS obligatorio prod, tokens single-use con TTL=1h.

R2.5

Vulnerabilidades libs

Parcial

Django 5.2 y Expo SDK 57 son versiones actuales. uv sync lockea versiones. Falta: pip-audit + npm audit automatizado en CI (planeado Sprint 12).

R2.6

Fallback en errores

Cumple

Fail-open explicito en filtro territorial (documentado + testeado). Cache invalidation via signals cuando cambia comuna. React Query maneja retry/dedup/cache. Guest mode como fallback si falla auth. Health check reporta degraded con HTTP 503 si DB cae.

R2.7

Reproducibilidad

Cumple

Setup en 5 comandos documentado en README. Fixtures + 6 management commands idempotentes con test test_seeds_ficticios.py. Environment variables via .env.example. Docker Compose planeado Sprint 12.

R2.8

Monitoreo produccion

No cumple

Deuda conocida y documentada. Existe health check pero sin Sentry / logging estructurado / metricas / alerting. Todo planeado Sprint 12 (deploy). Es el gap real mas grande de R2.

Lo que se puede afirmar en la tesis

El backend tiene cobertura funcional exhaustiva: cada endpoint tiene test, cada refactor mayor tiene test de regresion, los signals estan validados, el fail-open esta testeado explicitamente, la seguridad tiene defensas activas testeadas (anti-enumeration, permission classes). El unico gap real de testing es la ausencia de tests frontend (Sprint 10 los agrega con RTL).

4 patrones de resiliencia implementados

Estos son patrones concretos que se pueden citar en la tesis para argumentar la robustez tecnica. Todos con evidencia en codigo y tests.

1. Fail-open territorial

Filtro territorial en views.py: si el usuario no tiene comuna registrada, o si su comuna no tiene UT registrada, retorna TODOS los candidatos sin filtrar. Prioriza disponibilidad sobre restriccion.

if comuna_usuario is None:
    return queryset  # fail-open

ut_votante = comuna_usuario.unidad_territorial
if ut_votante is None:
    return queryset  # fail-open (datos incompletos)

ids_permitidos = {ut_votante.id} | {a.id for a in ut_votante.ancestros}
return queryset.filter(
    Q(unidad_territorial__isnull=True) |
    Q(unidad_territorial_id__in=ids_permitidos)
)

Test: test_matching_territorial.py caso test_sin_comuna_ve_todos. Evita que un bug de datos deje al usuario sin candidatos.

2. Anti user-enumeration

Password reset devuelve ResetError generico ante cualquier error (email no existe, email deshabilitado, rate limit). El atacante no puede saber si un email esta registrado.

POST /api/v1/password-reset/request/
{ "email": "existe@x.cl" }
--> 200 OK "Si el email existe, recibiras un enlace"

POST /api/v1/password-reset/request/
{ "email": "no-existe@x.cl" }
--> 200 OK "Si el email existe, recibiras un enlace"

Test: test_password_reset.py. Token single-use con TTL=1h (PasswordResetToken.TTL_HOURS = 1).

3. Cache invalidation via signals

La cache de tipos_base se invalida automaticamente via signals post_save + post_delete de TipoEleccion. Sin drift entre cache y DB.

@receiver(post_save, sender=TipoEleccion)
@receiver(post_delete, sender=TipoEleccion)
def _invalidar_cache_tipos_base(sender, **kwargs):
    invalidar_cache_tipos_base()

# Verificado con CaptureQueriesContext:
# - hit: 0 queries
# - miss (post-invalidacion): 1 query

Test: test_services_tipos.py. Mismo patron para UserProfile.comuna -> invalida matches viejos.

4. Health check con degraded state

Endpoint /api/v1/health/ publico. Ejecuta SELECT 1 contra la DB. Si DB responde: HTTP 200 con status="ok". Si DB falla: HTTP 503 con status="degraded".

GET /api/v1/health/
--> 200 {
  "status": "ok",
  "api_version": "1.0.0",
  "django_version": "5.2.x",
  "debug": false,
  "checks": { "database": "ok" }
}

# Si DB cae:
--> 503 { "status": "degraded", ... }

Test: test_meta.py::TestHealthCheck. Preparado para load balancer / kubernetes liveness probe.

Gaps reales y plan concreto

Los 3 gaps de R2 (todos ya documentados como deuda tecnica en buenas-practicas.md). El proyecto es honesto sobre lo que falta.

Gap 1: 0% cobertura frontend

Sprint 10

Backend tiene 25 tests. Frontend TypeScript/React Native tiene 0 tests. Es el gap mas grande de R2.3.

Plan concreto: Jest + React Testing Library + jest-expo. Prioridad:
  1. Services puros (matching, cuestionario) - deberian ser 100% cubiertos
  2. Stores (Zustand slices) - hooks aislados
  3. API hooks (React Query) - mock server con MSW
  4. Componentes primitivos (Pressable, forms) - RTL con user-event
  5. Screens - smoke tests + interacciones criticas

Impacto en tesis: agregar seccion "Deuda tecnica: testing frontend" honesta.

Gap 2: Sin Sentry / observabilidad

Sprint 12

Existe health check pero no hay logging estructurado, metricas, tracing ni alerting. R2.8 es el sub-req mas debil de matchVote.

Plan concreto:
  1. Sentry SDK Django + React Native (free tier alcanza)
  2. Logging estructurado JSON con correlation IDs
  3. Metricas basicas: request rate, error rate, latency (django-prometheus)
  4. Uptime monitoring externo (UptimeRobot free / BetterUptime)
  5. Alertas por email en error rate {'>'} umbral

Impacto en tesis: presentar como "post-MVP, pre-produccion".

Gap 3: Sin scanning automatizado de dependencias

Sprint 12

Django 5.2 y Expo SDK 57 estan actuales, pero no hay auditoria automatica en cada push.

Plan concreto:
  1. GitHub Actions con pip-audit + npm audit --production en cada PR
  2. Dependabot automatic PRs para updates de seguridad
  3. Snyk free tier (limitado pero suficiente para MVP)

Impacto en tesis: minimo, es un check automatizable en 1 tarde.

Argumentos concretos para la tesis

Que afirmar (con evidencia)

  • • matchVote scorea 78% en R2 EGTAI, el mas alto entre los VAAs comparables.
  • • 25 archivos de tests backend con cobertura funcional completa (todos los endpoints, refactors mayores, signals, seeds).
  • • 4 patrones de resiliencia implementados y testeados: fail-open, anti-enumeration, cache invalidation, health check con degraded.
  • • Modelo de permisos estratificado: 26 endpoints con permission class explicita por endpoint, no todo-o-nada.
  • • Guest mode: la app funciona sin cuenta - fallback y feature al mismo tiempo.
  • • Reproducibilidad completa: setup en 5 comandos, fixtures + 6 seeds idempotentes con test.

Que reconocer honestamente

  • • 0% cobertura frontend - gap real, Sprint 10 planeado.
  • • Sin observabilidad en produccion (Sentry/metrics/logs) - Sprint 12.
  • • Sin pentest formal - defensas existen (anti-enum, permission classes, HTTPS) pero no validadas externamente.
  • • Sin scanning automatizado de vulnerabilidades - facil de agregar.
  • • Sin CI/CD - los tests existen pero corren manualmente.
  • • SQLite en dev vs PostgreSQL en prod - deuda de parity documentada.
"The robustness of the app is not about being invulnerable, but about being honest about its failure modes and testing them explicitly."

Cita adaptable para la tesis. matchVote documenta y testea sus modos de falla (fail-open, degraded, guest fallback) en vez de asumir que todo va a andar bien. Es un enfoque de ingenieria defensiva.
